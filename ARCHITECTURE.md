# ZorgTechAdvies Commercial Intelligence Operating System

## 1. Purpose

This repository integrates positioning, propositions, lead intelligence, expert content, website publishing and commercial learning into one operating system.

The system is designed for a small, named B2B market. Content is not an isolated marketing engine. Market intelligence and account signals identify where attention is useful; expertise content builds recognition and trust; verification converts hypotheses into qualified conversations; the customer phase determines the appropriate proposition.

## 2. Canonical flow

`Named market -> signals & evidence -> screening -> phase hypothesis -> verification -> proposition routing -> content/direct distribution -> conversation -> qualified opportunity -> delivery -> case/evidence -> doctrine`

## 3. Core state discipline

Never collapse these states:

1. **FACT** — directly supported by a recorded source.
2. **INFERENCE** — interpretation derived from one or more facts.
3. **HYPOTHESIS** — plausible account phase, need or proposition to verify.
4. **VERIFIED_FACT** — confirmed through direct contact or authoritative evidence.
5. **COMMERCIAL_DECISION** — explicit decision to contact, nurture, pursue, park or propose.

This separation applies to lead intelligence, research and public content.

## 4. Commercial architecture

The KetenScan remains the flagship first step when the organisation's real problem, scope or route is not sufficiently clear. It is not a mandatory toll gate. An account already in a different phase can enter through the corresponding proposition.

External positioning should remain focused. The website should not become a catalogue of seven equal services. The portfolio is primarily a routing model behind one doctrine.

## 5. Content architecture

The book *Zorgdomotica als zorgkritische keten* is the doctrine and primary evergreen content inventory.

Editorial production combines:

`book doctrine x current anchor x customer phase x original ZorgTechAdvies insight x practical instrument x next step`

Default cadence after bootstrap:

- one LinkedIn expertise moment per week;
- one source-grounded core article per month;
- one practical instrument every 1–2 months;
- no separate monthly newsletter production until audience/list justifies it.

## 6. Website architecture

The homepage remains KetenScan-led. Add, rather than replace:

- a phase-aware path: "Waar staat uw organisatie nu?";
- a compact view of possible next-step propositions;
- a knowledge/inzichten layer;
- an evidence layer including an example KetenScan and future cases;
- editorial-method transparency.

Website source and content are versioned in this repository. Production deployment is from GitHub to Cloudflare. Direct manual edits to production are deprecated once migration is complete.

## 7. Delivery architecture

Recommended target:

- static-first site generator;
- Markdown/MDX for articles and structured proposition content;
- GitHub-backed publishing;
- Cloudflare Pages Git integration with preview deployments;
- optional Git-based CMS UI for small editorial changes, while Git remains canonical.

## 8. AI architecture

AI is used where output is verifiable against existing material:

- signal triage;
- source extraction;
- repurposing from approved core content;
- structure/draft assistance with empty source placeholders;
- consistency checking against doctrine and style rules.

AI must not autonomously:

- publish externally;
- fabricate or infer sources;
- mass-personalise outreach;
- turn a hypothesis into a commercial fact;
- rank vendors without an approved method and evidence basis.

## 9. Measurement architecture

Primary measures:

- named-market reachable coverage;
- qualified conversations per quarter and proposition;
- phase-hypothesis accuracy;
- stated source of awareness in intake;
- qualified pipeline/value once sample size exists.

Vanity reach is diagnostic, not a primary success metric.

## 10. Source-of-truth rule

If strategy, scoring logic, content or website differs between GitHub and an exported file, GitHub wins unless a documented migration decision says otherwise.
