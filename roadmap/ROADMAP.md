# ZorgTechAdvies Roadmap

Updated: 2026-08-14

## North star

Build a credible, repeatable commercial intelligence system in which GitHub is the canonical source for doctrine, proposition logic, lead methodology, content and website; evidence and conversations continuously improve the system.

## Phase 0 — Architecture freeze and repository bootstrap

**Status:** in progress

Outputs:

- integrated architecture;
- positioning and commercial operating model;
- customer phase vocabulary;
- proposition routing;
- lead-intelligence v3.2 specification;
- editorial method and quality gates;
- website architecture and deployment policy;
- roadmap and metrics.

Exit condition: no material contradiction remains between commercial model, content framework, lead model and website strategy.

## Phase 1 — Commercial foundation (approximately weeks 1–6)

Priority order:

1. operationalise source class B (TenderNed/Mercell/TED searches);
2. migrate v3.1 logic to v3.2 terminology/states;
3. start named-market register without publishing personal lead data in this public repo;
4. test current CONTACT accounts with verification questions;
5. start systematic LinkedIn connection/engagement routine;
6. produce a strong example KetenScan;
7. establish doctrine/style contracts for AI-supported work;
8. publish the first 1–2 core authority pieces;
9. decide Cloudflare migration path and capture exact current website source.

## Phase 2 — Evidence and corpus (approximately weeks 7–12)

Outputs:

- approximately five strong authority assets total;
- stable weekly LinkedIn rhythm;
- practical instrument publication started;
- ROUTE accounts tested against actual customer phase;
- signal-triage and repurposing workflows operating;
- at least ten real account conversations/verification outcomes recorded;
- example KetenScan actively used in sales conversations;
- website knowledge archive live or ready for deployment.

Learning gate: compare phase hypothesis with actual phase. Do not materially change weights merely because the spreadsheet "feels" wrong.

## Phase 3 — Website migration and Git-first publishing

Can run partly in parallel with phases 1–2.

Steps:

1. obtain exact current production source or reconstruct current live site with visual parity;
2. migrate to Astro static-first architecture;
3. create Markdown/MDX insight collections;
4. implement `/inzichten/` archive and article template;
5. add lightweight phase-aware section to homepage;
6. add example-KetenScan evidence block/page;
7. connect GitHub to Cloudflare build/deploy path;
8. validate branch/PR previews;
9. perform content, responsive and visual parity checks;
10. switch production domain only after approval;
11. retire manual loose-HTML publishing.

## Phase 4 — Proprietary intelligence

Run an 8–12 hour feasibility sprint for the proposed replacement-wave research.

Success criteria before scaling:

- enough organisations have traceable original livegang/major renewal dates;
- system/platform attribution is reliable enough;
- sources can be published or cited transparently;
- resulting horizon is framed as an indicator, not a promised replacement date.

If viable, scale to a flagship research dossier and serialised content. If not viable, publish a smaller analysis and stop.

## Phase 5 — Scale only after traction

Potential decisions:

- launch `KetenSignaal` as a recurring email/newsletter;
- add Git-backed CMS UI if GitHub editing friction warrants it;
- expand publication frequency;
- develop Flanders actively;
- change lead-model source weights based on sufficient observations;
- add deeper automation/CRM integration.

## Priority override

A qualified live conversation, proposal or delivery may displace a planned publication. Do not protect content cadence at the expense of real commercial progress.
